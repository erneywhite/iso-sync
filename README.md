PHP-скрипты, которые держат локальное зеркало ISO-образов свежим. Они качают новые релизы Debian, Ubuntu, CentOS, AlmaLinux, Proxmox, ArchLinux и VirtIO-win с официальных серверов и сверяют SHA256, а где есть GPG-подписи, проверяют и их. Если установлен `aria2c`, файлы качаются в несколько потоков. Каждый прогон пишет структурированный лог и сводку, а результат видно на веб-странице зеркала.

С Windows иначе. Публичных зеркал его образов нет и не будет: лицензия запрещает перераздачу. Поэтому образы Windows не качаются, а собираются из официальных пакетов обновлений, которые Microsoft раздаёт открыто. Подробнее — в разделе [Образы Windows](#образы-windows).

> [!TIP]
> **Живое демо:** [iso.erney.monster](https://iso.erney.monster) — публичное зеркало автора, обновляется по cron.

## Возможности

### Синхронизация
- Сверка SHA256 с официальными `SHA256SUMS` / `SHA256SUM` / `CHECKSUM`
- Проверка GPG-подписей, если она включена (`SHA256SUMS.gpg` / `.sign` / `.asc`)
- Повторная проверка хэша после загрузки и сверка `Content-Length`
- Четыре режима выбора версии: `fixed` / `latest` / `family` / `discovery` — от точного имени файла до автоподхвата будущих релизов Ubuntu по диапазону папок
- Атомарная подмена через `*.tmp` + `rename()`, resume по HTTP Range

### Скорость и надёжность
- Если в `PATH` есть `aria2c`, файлы качаются в несколько потоков, в 2–4 раза быстрее; без него работает настроенный cURL
- До 5 попыток с прогрессивной задержкой, прерывание при 60 сек без прогресса
- Оба скрипта держат блокировку `flock`, поэтому повторный запуск из cron не наслаивается на текущий
- Per-entry `ip_version: v4|v6|any` для обхода IPv4-блоков (см. кейс Proxmox в [Конфигурации](#режим-3-family--динамическое-имя-по-шаблону--cleanup-старых))

### Образы Windows
- Сборка из официальных пакетов Microsoft через UUP dump: зеркал для Windows нет, лицензия их не допускает
- Канал задаётся явно (`title_pattern`), а не «самое свежее по дате»: иначе вместо стабильной GA приезжает Insider-билд
- SHA1 каждого пакета проверяет `aria2` при загрузке; докачка после обрыва, пропуск уже собранного, ротация прошлых версий
- Windows 11, Windows Server 2025, Windows 10 — проверено на практике

### Приватные каталоги
- Маркер `.private` убирает каталог из листинга, тоталов и «Истории обновлений»
- Allowlist по IP/CIDR (v4 и v6) прямо в маркере: со своих адресов каталог виден и помечен плашкой `PRIVATE`
- `X-Forwarded-For` читается только от доверенных прокси из конфига, иначе листинг открыл бы любой подставленный заголовок

### Безопасность по умолчанию
- SSL-проверка включена; отключение точечно через `insecure_ssl: true` для конкретного зеркала
- GPG-блоки готовы для Debian/Ubuntu — нужен только импорт ключей в системный keyring

### Веб-интерфейс
- Три колонки: разделы с логотипами ОС, список файлов и сведения о выбранном файле. Тема тёмная, имена файлов и хэши набраны моноширинным шрифтом
- Поиск по имени или по SHA-256: Ctrl/Cmd+K открывает поиск, Esc сбрасывает
- Отметка «новейший» считается по семействам: у Proxmox VE 9, Backup 4 и Mail Gateway 7 она своя. Сортировка по версии, дате или размеру
- У каждого файла есть прямая ссылка и команда `wget`, обе копируются одной кнопкой. SHA-256 показан группами по 8 символов, так его удобно сверять глазами
- Слева сводка последней проверки, справа выезжает история обновлений, под списком показаны файлы, которых нет на диске
- Страница целиком не прокручивается, прокручивается только список. Сборка не нужна, шрифты и скрипты лежат в репозитории

### Эксплуатация
- Структурированные JSON-логи в `logs/update.log` и `logs/hashes.log` — удобно парсить из `jq`, отдавать в Loki/Elastic
- Сводка последнего прогона в `logs/last_run.json`, её показывает веб-интерфейс
- Кэш SHA256 по `mtime + size`: если файл не менялся, хэш заново не считается

## Быстрый старт

```bash
git clone https://github.com/erneywhite/iso-sync.git
cd iso-sync
mkdir -p files logs .hash_cache && chmod -R 755 files logs

# (рекомендуется — multi-stream загрузка, x2-x4 быстрее)
sudo apt install aria2

# Первый прогон
php update_iso.php
```

Для веб-интерфейса — поместите папку в `DocumentRoot` веб-сервера (Apache / nginx + PHP-FPM), откройте `index.php`. Cron-задания — см. [Автоматизация через cron](#автоматизация-через-cron).

> [!IMPORTANT]
> Для Debian и Ubuntu в дефолтной конфигурации включена GPG-проверка. Без импорта ключей в системный keyring загрузка этих образов будет падать с `GPG verify FAILED`. См. [Безопасность → GPG-верификация](#gpg-верификация-sha256sums) или временно удалите блоки `gpg` из `config/iso-list.json`.

## Требования

- PHP 8.1+ с расширением `cURL` (проверено на 8.4)
- Доступ в интернет для скачивания контрольных сумм и образов
- Права на запись в `files/`, `.hash_cache/`, `logs/`
- Достаточно свободного места на диске (каждый DVD-образ — 4–8 ГБ)
- *(Желательно)* `aria2c` в PATH: качает в несколько потоков, в 2–4 раза быстрее cURL. `apt install aria2`
- *(Если включена проверка подписи)* `gpg` в PATH
- *(Только для сборки Windows)* тулчейн конвертера: `apt install aria2 cabextract wimtools chntpw genisoimage`, плюс ~40 ГБ свободного места на время сборки. Проверить готовность: `php diag_uup.php`

Проверить наличие cURL:

```bash
php -r "echo extension_loaded('curl') ? 'OK' : 'NOT FOUND';"
```

## Установка

```bash
git clone https://github.com/erneywhite/iso-sync.git
cd iso-sync
mkdir -p files logs .hash_cache
chmod -R 755 files logs
```

Для веб-интерфейса поместите папку в `DocumentRoot` вашего веб-сервера (Apache / nginx + PHP-FPM).

> [!NOTE]
> В репозитории включён `.gitattributes` с `* text=auto eol=lf`. Это нужно для серверов с панелями типа aaPanel/baota: без него на Linux появлялись бы CRLF/LF mismatch и `git pull` падал с `local changes would be overwritten`. При деплое через панель вместо `git pull` используйте `git fetch origin main && git reset --hard origin/main`.

## Использование

### `update_iso.php` — проверка и загрузка

```bash
php update_iso.php
```

Проверяет каждую запись из `config/iso-list.json` и скачивает новую версию, если она вышла. В конце сам запускает `generate_all_hashes.php`. Скрипт держит блокировку `flock`: если предыдущий запуск ещё работает, повторный (например, из cron) тихо выходит с кодом 0.

Код возврата:

- `0` — все файлы актуальны или успешно обновлены
- `1` — были ошибки (детали в `logs/update.log` и `logs/last_run.json`)
- `2` — фатальная ошибка (битый конфиг, нет доступа к каталогам и т.п.)

### `generate_all_hashes.php` — пересчёт хэшей

```bash
php generate_all_hashes.php
```

Обходит `files/` рекурсивно, считает SHA256 каждого файла и складывает результат в кэш `.hash_cache/`. Записи удалённых файлов из кэша убирает. Тоже держит блокировку `flock`.

### `build_uup.php` — сборка образов Windows

```bash
php build_uup.php --dry-run              # что будет собрано, без загрузки
php build_uup.php                        # собрать всё включённое в конфиге
php build_uup.php --entry=windows-11-25h2  # только одну запись
php build_uup.php --list='Windows Server'  # что вообще есть в базе UUP
```

У сборки свой скрипт, своя блокировка и своё расписание: она идёт часами и нагружает диск и процессор, а `update_iso` — быстрая проверка. Подробности — в разделе [Образы Windows](#образы-windows).

## Веб-интерфейс

Откройте `index.php` в браузере. Данные PHP собирает на сервере и отдаёт вместе с разметкой (`window.ISO_ARCHIVE_DATA`), а `assets/app.js` только рисует страницу. Сборка, npm и внешние CDN не нужны: шрифты, иконки и скрипты лежат в репозитории.

Страница занимает ровно высоту окна: прокручиваются только список файлов, панель сведений и меню разделов, подвал всегда виден внизу. Вёрстка рассчитана на компьютер, мобильная не делалась.

### Боковая панель

- Разделы — подпапки `files/` с логотипами ОС в фирменных цветах и числом файлов. Первым идёт «Все файлы», он открыт по умолчанию. Подпись раздела может отличаться от имени папки: папка `Windows` показана как «Windows utils», ссылки при этом не меняются. Файлы, лежащие прямо в `files/`, видны во «Все файлы».
- Под разделами — общий объём архива, число файлов и разделов. Приватные каталоги в эти цифры не входят (см. [Приватные каталоги](#приватные-каталоги)).
- Ниже — сводка последнего прогона `update_iso.php` из `logs/last_run.json`: когда он закончился и сколько шёл, сколько файлов обновлено, актуально, пропущено и с ошибками. Ошибки выделены красным, при фатальном завершении показан текст ошибки. Если прогонов ещё не было, так и написано.

### Список файлов

- Имя, размер и дата файла. Дата — день релиза на апстриме, а не время скачивания. Под именем подписан раздел (во «Все файлы» и в поиске) и «хэш не готов», если SHA-256 ещё не посчитан.
- Отметка «новейший» стоит у самой свежей версии в каждом семействе, например отдельно у Proxmox VE 9, Proxmox Backup 4 и Proxmox Mail 7. Она считается по всему каталогу, поэтому поиск и сортировка её не переносят.
- Сортировка — по версии, по дате файла или по размеру.
- Над списком раздела — строка «Новейшая версия» с кнопкой скачивания.

### Панель сведений о файле

Открывается по клику на файл. В ней размер, дата, SHA-256 (группами по 8 символов, чтобы сверять глазами), прямая ссылка и готовая команда `wget`, у каждого — кнопка «Копировать». Внизу кнопка «Скачать файл». Копирование идёт через Clipboard API, а если браузер его не даёт, через запасной путь; результат сообщает всплывающая подсказка в углу.

### Поиск

По имени файла, имени папки раздела и SHA-256 — достаточно начала хэша. Ищет по всему архиву, а не только в текущем разделе. `Ctrl/Cmd+K` ставит курсор в поиск (и в русской раскладке), `Esc` сбрасывает поиск и закрывает историю, крестик в поле — очищает.

### Дополнительно

- Кнопка «Обновления» справа вверху выдвигает панель с последними событиями из `logs/update.log`: что обновилось (зелёным), что удалено при чистке старых версий (серым), что не удалось скачать (красным). Показываются только имена файлов, без серверных путей. «Закрыть» стоит на месте кнопки «Обновления», так что панель открывается и закрывается, не сдвигая мышь.
- Блок «Отсутствующие файлы» показывает записи конфига, которых нет на диске, с папкой и ожидаемым файлом на апстриме. Family- и discovery-записи сюда не попадают: их фактические имена известны только во время `update_iso.php`.
- Если раздел пуст или поиск ничего не нашёл, вместо списка показывается пояснение.

Анимация панели истории отключается при системной настройке `prefers-reduced-motion: reduce`.

Шрифты — IBM Plex Sans для интерфейса и JetBrains Mono для имён файлов, размеров, дат и хэшей; оба лежат в `assets/fonts`. Цвета, шрифты и отступы заданы переменными в начале `assets/styles.css`, поэтому палитру меняют в одном месте.

> [!NOTE]
> CSS и JS подключаются с версией в адресе (`assets/app.js?v=…`). При правке статики поднимите версию в `index.php`, иначе браузеры посетителей возьмут старый файл из кэша.

## Конфигурация

Список образов хранится в [`config/iso-list.json`](config/iso-list.json). Поддерживаются четыре режима выбора версии:

### Режим 1: `fixed` — точное имя

Когда нужен конкретный файл по имени:

```jsonc
"Debian_12.iso": {
    "local_subdir": "Debian",
    "url_dir":      "https://cdimage.debian.org/cdimage/archive/12.12.0/amd64/iso-dvd/",
    "remote_name":  "debian-12.12.0-amd64-DVD-1.iso"
}
```

### Режим 2: `latest` — фиксированное локальное имя, авто-выбор внутри папки

Когда внутри одного URL зеркала точечная версия меняется (Ubuntu 22.04.5 → 22.04.6, CentOS Stream snapshots), но локальный файл всегда хочется называть одинаково:

```jsonc
"Ubuntu_22.04.iso": {
    "local_subdir":   "Ubuntu",
    "url_dir":        "https://releases.ubuntu.com/22.04/",
    "remote_name":    "latest",
    "latest_pattern": "/^ubuntu-22\\.04(?:\\.\\d+)?-live-server-amd64\\.iso$/"
}
```

Среди файлов в `SHA256SUMS`, совпадающих с `latest_pattern`, выбирается версионно-старший по `strnatcasecmp`. Локальный файл всегда сохраняется как `Ubuntu_22.04.iso`.

### Режим 3: `family` — динамическое имя по шаблону + cleanup старых

Когда апстрим публикует целую серию версий в одной папке (`proxmox-backup-server_4.0-1.iso`, `4.1-1.iso`, `4.2-1.iso`...) и хочется автоматически держать локально только самую свежую с версией в имени:

```jsonc
"proxmox-backup-4": {
    "local_subdir":        "Proxmox",
    "url_dir":             "https://de.cdn.proxmox.com/iso/",
    "ip_version":          "v6",
    "remote_pattern":      "/^proxmox-backup-server_4\\.(\\d+)-\\d+\\.iso$/",
    "local_name_template": "Proxmox_BackUP_4.{1}.iso",
    "cleanup_old":         true
}
```

Что произойдёт:

1. В `SHA256SUMS` найдены `proxmox-backup-server_4.0-1.iso`, `4.1-1.iso`, `4.2-1.iso`
2. Среди них старший — `4.2-1.iso` → captures: `[1] = "2"`
3. Локальное имя: `Proxmox_BackUP_4.{1}.iso` → `Proxmox_BackUP_4.2.iso`
4. После успешной загрузки старые `Proxmox_BackUP_4.0.iso`, `Proxmox_BackUP_4.1.iso` удаляются (т.к. `cleanup_old: true`)

JSON-ключ записи (`proxmox-backup-4`) — произвольный идентификатор семейства, не используется как имя файла.

> [!WARNING]
> **Почему `de.cdn.proxmox.com` + `ip_version: v6`, а не `download.proxmox.com`?** Официальный CDN Proxmox по **IPv4** дропает TCP-трафик из ряда хостинговых сетей (например netcup AS197540) — соединение таймаутит, хотя DNS резолвит корректно. По **IPv6** трафик проходит, но сертификат CDN-узла не содержит имя `download.proxmox.com` (в SAN только `enterprise.proxmox.com` + `*.cdn.proxmox.com`). Поэтому скрипт обращается к узлу `de.cdn.proxmox.com` напрямую: имя есть в SAN, и сертификат валиден. Ходит он по IPv6 (`ip_version: v6`), так что блокировка IPv4 не мешает, а контент свежий, потому что это официальный CDN, а не зеркало.
>
> Если у вас всё доступно по IPv4 — верните `url_dir` на `https://download.proxmox.com/iso/` и уберите `ip_version`. Зеркала (mirrors.xtom.de, mirrors.tuna…) — крайний случай: каталог `/iso/` на них сильно отстаёт от CDN.

### Режим 4: `discovery` — перебор папок по диапазону

Когда апстрим разносит мажорные версии по разным папкам (Ubuntu LTS: `/22.04/`, `/24.04/`, `/26.04/` ...) и хочется автоматически подхватывать будущие релизы. Скрипт сам генерирует список папок по диапазону, для каждой пробует SHA256SUMS, существующие — обрабатывает как family с подставленным `{folder}`:

```jsonc
"ubuntu-lts": {
    "local_subdir":        "Ubuntu",
    "url_template":        "https://releases.ubuntu.com/{folder}/",
    "folder_enum":         { "from": 22, "to": 30, "step": 1, "format": "{0}.04" },
    "remote_pattern":      "/^ubuntu-{folder}(?:\\.\\d+)?-live-server-amd64\\.iso$/",
    "local_name_template": "Ubuntu_{folder}.iso"
}
```

Что произойдёт:

1. `folder_enum` сгенерирует `["22.04","23.04","24.04",...,"30.04"]` (9 папок)
2. Для каждой будет пробный HEAD на `<url_template>/SHA256SUMS`. Если 404 — папка пропускается тихо.
3. Для существующих (на момент запуска: 22.04, 24.04, 25.04) — `{folder}` подставляется в `url_dir`, `remote_pattern`, `local_name_template` (с `preg_quote` для regex), и запускается обычная family-обработка
4. Внутри `/22.04/` regex `^ubuntu-22\.04(?:\.\d+)?-live-server-amd64\.iso$` ловит файл — берётся версионно-старший (когда выйдет 22.04.6 вместо .5, подхватится автоматом)
5. Локальное имя: `Ubuntu_{folder}.iso` → `Ubuntu_22.04.iso`

Чтобы брать только LTS, поставьте `step: 2`: будут выбраны чётные 22, 24, 26, 28, 30. С `step: 1` в диапазон попадают и промежуточные релизы вроде 23.04 и 25.04.

Новые релизы попадают в диапазон без правок конфига: как только на апстриме появится папка, например `/28.04/`, скрипт начнёт её качать.

<details>
<summary><b>Все поля записи конфига</b> — полная справка</summary>

| Поле | Режим | По умолчанию | Описание |
|------|-------|-------------|----------|

## Образы Windows

Зеркал для Windows нет и не появится: лицензия Microsoft запрещает третьим лицам перераздавать образы. Поэтому на нормальных зеркалах их нет, они встречаются только на сомнительных сайтах. Зато официальные пакеты обновлений Microsoft раздаёт открыто, и из них собирается полноценный ISO. Этим занимается [`build_uup.php`](build_uup.php).

Файлы качаются не с uupdump, он отдаёт только список. Сами пакеты идут с `tlu.dl.delivery.mp.microsoft.com`, то есть с серверов Microsoft.

```jsonc
"windows-11-25h2": {
    "enabled":       true,
    "local_subdir":  "Windows OS",
    "name_template": "Windows_11_25H2_{build}_{lang}_x64.iso",
    "title_pattern": "/^Windows 11, version 25H2 /",
    "arch":          "amd64",
    "lang":          "en-us",
    "edition":       "PROFESSIONAL",
    "cleanup_old":   true
}
```

> [!IMPORTANT]
> Канал задаётся `title_pattern`, а не сортировкой по дате. В базе UUP свежайшие по дате записи — preview-ветки, и «взять самое новое» тихо притащит Insider-билд вместо стабильной GA. Заметить это можно уже постфактум, на зеркале.

Заголовки в базе не всегда очевидны: Windows 10 подписана как `Feature update to Windows 10, version 22H2`, хотя под этим именем лежит полноценный образ, а не патч. Фактические заголовки показывает `--list`.

SHA1 каждого пакета проверяет `aria2` при загрузке: у собранного ISO нет чек-суммы на апстриме, поэтому порчу ловят на уровне исходных файлов. Оборванная загрузка продолжается с места остановки, готовый образ с прошлого прогона не пересобирается, свободное место проверяется до старта, а блокировка не даёт двум сборкам наложиться.

Полное описание — [`docs/UUP-BUILDS.md`](docs/UUP-BUILDS.md).

## Приватные каталоги

Если на зеркале лежит то, что не предназначено для публичной раздачи (те же образы Microsoft), положите в каталог файл-маркер `.private`, и каталог пропадёт из листинга, тоталов и «Истории обновлений».

В маркер можно вписать адреса, с которых каталог всё-таки виден:

```
# дом
203.0.113.42
# офис
198.51.100.0/24
2001:db8:1234::/48
```

Поддерживаются IPv4 и IPv6, одиночные адреса и подсети. Когда каталог показан по allowlist, он помечается плашкой `PRIVATE`, чтобы его не спутали с публичной раздачей.

> [!WARNING]
> Маркер — это **витрина, а не защита**. Каталог исчезает из UI, но веб-сервер продолжает отдавать файлы по прямой ссылке. Реальный доступ закрывается тем же списком IP в nginx (`allow` / `deny all`) — см. [`docs/PRIVATE-DIRS.md`](docs/PRIVATE-DIRS.md).

Клиент определяется по `REMOTE_ADDR`. `X-Forwarded-For` читается, только если сам `REMOTE_ADDR` есть в [`config/trusted-proxies.txt`](config/trusted-proxies.txt), иначе приватный листинг открывал бы любой, кто подставит заголовок. Для связки nginx + Apache (частый режим aaPanel) это как раз тот случай: PHP видит `127.0.0.1`, а настоящий адрес приходит в заголовке.

## Логика обновления

Для каждой записи из конфига:

```
1. Скачать SHA256SUMS / SHA256SUM / CHECKSUM (по списку checksum_files)
   ├─ Не найдены
   │   ├─ force_download_without_checksum=true и режим fixed/latest
   │   │   └─ Загрузка без проверки хэша
   │   └─ Иначе → failed
   └─ Найдены
       ├─ (опционально) проверить GPG-подпись SHA256SUMS
       └─ Резолв имени удалённого файла:
           ├─ family    → среди совпавших с remote_pattern взять версионно-старший
           ├─           ├─ имя локального файла = local_name_template с {1},{2},...
           ├─ latest    → среди совпавших с latest_pattern взять версионно-старший
           ├─           ├─ имя локального файла = ключ JSON-записи
           └─ fixed     → точное имя из remote_name
                         ├─ имя локального файла = ключ JSON-записи

2. Сравнение хэшей:
   - SHA256 локального файла (из кэша по mtime+size, иначе hash_file())
   - Совпали → up_to_date, выходим
   - Иначе → переходим к загрузке

3. Загрузка:
   - HEAD-запрос → ожидаемый Content-Length и Last-Modified
   - При skip_if_unchanged=true и неизменном remote — пропуск
   - До 5 попыток, прерывание при 60 сек без прогресса
   - После загрузки: проверка фактического размера == Content-Length
   - Если был ожидаемый хэш — пере-проверка SHA256 файла .tmp
   - rename(.tmp, финальный файл) — атомарно
   - Кэш SHA256 обновляется сразу

4. Family + cleanup_old + успешный update → удаление старых версий в той же подпапке,
   чьи имена матчатся с template-как-regex (но не равно текущему).

5. Запуск generate_all_hashes.php — пересчёт по всем файлам и чистка осиротевшего кэша.

6. Запись logs/last_run.json со сводкой.
```

## Скорость загрузки

### aria2c (рекомендуется)

При наличии `aria2c` в `PATH` `update_iso.php` автоматически использует его вместо cURL для скачивания ISO. Файл делится на 16 сегментов и качается параллельно через HTTP Range. Так обходится ограничение скорости на одно соединение, которое ставят многие серверы (Proxmox, Microsoft, зеркала на AWS S3), и на практике загрузка ускоряется в 2–4 раза. Установка:

```bash
apt install aria2          # Debian / Ubuntu
dnf install aria2          # Fedora / RHEL
```

При запуске `update_iso.php` пишет в лог, чем будет качать:

```
Использую aria2c для загрузки: /usr/bin/aria2c
```

или (если не установлен):

```
aria2c не найден, использую cURL-Downloader (apt install aria2 для ускорения)
```

`aria2c` сам показывает прогресс-бар и скорость. После загрузки скрипт сверяет SHA256 и Content-Length, так что и через aria2c битый файл не пройдёт.

### Тюнинг cURL

Когда aria2c недоступен, штатный cURL-downloader использует:

- буфер чтения 256 KB (вместо дефолтных 16 KB)
- `TCP_NODELAY` (выключен Nagle)
- `TCP_KEEPALIVE`
- HTTP/1.1 (быстрее HTTP/2 для single-stream загрузок ISO)
- IPv4 (стабильнее на большинстве хостингов; переопределяется per-entry через `ip_version`)
- прогресс-бар throttle до 4 Hz (меньше fflush-overhead)

Вместе это даёт прибавку 20–50 % к скорости по сравнению с cURL по умолчанию.

## Безопасность

### SSL

Сертификаты проверяются по умолчанию (`CURLOPT_SSL_VERIFYPEER = true`). Если конкретное зеркало отдаёт битый или самоподписанный сертификат, добавьте этой записи в конфиге `"insecure_ssl": true`. Проверка отключится только для неё, остальные записи проверяют SSL как обычно.

### GPG-верификация SHA256SUMS

Подпись на `SHA256SUMS` защищает от подмены контрольных сумм по пути (MITM): кто подменит хэш, должен ещё и заново подписать файл, а без закрытого ключа это невозможно. В конфиге уже включены `gpg`-блоки для Debian и Ubuntu, но работают они, только если на сервере импортированы нужные ключи.

> [!WARNING]
> Без ключей загрузка Debian/Ubuntu будет падать с `GPG verify FAILED`. Импортируйте ключи (см. ниже) или удалите блоки `gpg` из `config/iso-list.json`.

<details>
<summary><b>Импорт GPG-ключей</b> (один раз)</summary>

```bash
# 1) Проверьте, что gpg установлен
apt install gnupg

# 2) Debian: импорт текущих Release/Archive ключей с keyring.debian.org
#    Актуальный список fingerprint'ов сверяйте на https://www.debian.org/CD/verify
#    На момент написания (Debian 11/12/13):
gpg --keyserver keyserver.ubuntu.com --recv-keys \
    DF9B9C49EAA9298432589D76DA87E80D6294BE9B \
    DC30D7C23CBBABEE \
    B7619EB16E91369B68B0E312EF0F382A1A7B6500

# 3) Ubuntu: импорт Ubuntu CD Image Automatic Signing Key
gpg --keyserver keyserver.ubuntu.com --recv-keys \
    843938DF228D22F7B3742BC0D94AA3F0EFE21092 \
    D94AA3F0EFE21092

# 4) Проверка: ключи импортированы?
gpg --list-keys
```

> Отпечатки ключей устаревают: Debian обновляет ключи с каждым релизом. Если `gpg --verify` падает с `Unknown signing key`, найдите актуальный отпечаток на странице Verify соответствующего проекта и импортируйте свежий.

</details>

#### Запуск под `www` (не root)

GPG читает ключи из `$HOME/.gnupg`. Если cron запускает `update_iso.php` от пользователя `www` (типично для aaPanel), ключи надо импортировать под этим пользователем:

```bash
su -s /bin/bash www -c 'gpg --keyserver keyserver.ubuntu.com --recv-keys 843938DF228D22F7B3742BC0D94AA3F0EFE21092'
```

#### Проверка работы

После импорта запустите `php update_iso.php`. В логе для Debian/Ubuntu записей должна появиться строка `GPG signature OK (fingerprint XXX...)`. Если видите `GPG verify FAILED`, ключ не импортирован под нужным пользователем или fingerprint устарел.

#### Проверка конкретного ключа

По умолчанию GPG-блок принимает подпись любым импортированным ключом. Чтобы принимать подпись только конкретного ключа, добавьте `key_fingerprint`:

```jsonc
"gpg": {
    "signature_url":   "https://cdimage.debian.org/.../SHA256SUMS.sign",
    "key_fingerprint": "DF9B9C49EAA9298432589D76DA87E80D6294BE9B"
}
```

При несовпадении запись помечается `failed`, файл не скачивается.

## Автоматизация через cron

Добавьте содержимое файла [`crontab`](crontab) в расписание (`crontab -e`), заменив `/path/to/` на реальный путь:

```cron
# Пересчёт хэшей каждый час
0 * * * *  php /path/to/generate_all_hashes.php > /dev/null 2>&1

# Обновление ISO ежедневно в полночь
# (внутри автозапускается generate_all_hashes)
0 0 * * *  php /path/to/update_iso.php > /dev/null 2>&1

# Сборка образов Windows — раз в неделю, отдельной задачей
30 4 * * 0  php /path/to/build_uup.php > /dev/null 2>&1
```

> [!NOTE]
> Скрипты держат блокировку `flock`: если запуски пересекутся, второй экземпляр тихо выйдет с кодом 0.
>
> При запуске не из TTY прогресс-бар автоматически переключается в компактный режим (логи не засоряются `\r`).

Про сборку Windows стоит знать два момента:

- **Разносить по времени с `update_iso`.** Локи у них разные, поэтому одновременный запуск не блокируется, а вот пересчёт хэшей общий и защищён своим локом: кто добежит вторым, тихо выйдет, и свежесобранный образ останется без SHA256 до следующего прогона.
- **Еженедельно — не расточительно.** Апстрим обновляется раз в месяц, и когда сборка не изменилась, прогон заканчивается сразу после одного запроса к API, ничего не качая. Зато свежий билд подхватывается в пределах недели, а не по фиксированной дате.

Если задачи заводятся через панель (aaPanel), в [`crontab`](crontab) описано, почему вывод скрипта может не попадать в лог задачи и как это чинится через `tee` с сохранением кода возврата.

## Тесты

Минимальный test-runner без зависимостей:

```bash
php tests/run.php
```

Покрытие:

- `ChecksumParserTest` — парсер `SHA256SUMS` (формат GNU/BSD/CRLF/комментарии/пробелы)
- `HashCacheTest` — кэш SHA256 (запись/чтение/инвалидация/чистка)
- `ConfigTest` — валидация JSON-конфига
- `FamilyResolverTest` — резолв шаблонов имён, версионная сортировка
- `DiscoveryTest` — генератор папок по диапазону
- `PrivateDirsTest` — CIDR-матчинг v4/v6, разбор allowlist, доверенные прокси
- `UupResolverTest` — выбор сборки: GA против preview, пакеты обновлений, сравнение ревизий
- `UupBuilderTest` — input для aria2, ротация версий, состояние сборок

Новый тест — это файл `tests/SomethingTest.php`, runner подхватит его сам.

CI гоняет тесты на PHP 8.1–8.4, плюс `php -l` по всем файлам и холостой прогон диагностик: тесты покрывают только `lib/`, а скрипты в корне ими не запускаются, и раньше опечатка в них всплывала уже на сервере. `mbstring` в матрицу намеренно не включён — на проде CLI-PHP собран без него, и окружение не должно быть щедрее боевого.

## Диагностика

Два отдельных скрипта, которые только читают и ничего не меняют. Их запускают на сервере, и вывод показывает, что не так.

```bash
php diag_private.php            # приватные каталоги: маркер, allowlist, IP из логов nginx
php diag_private.php 203.0.113.42   # плюс проверка конкретного адреса
php diag_uup.php                # готовность к сборке: тулчейн, место, сеть до CDN Microsoft
```

`diag_uup.php` проверяет не «отвечает ли хост», а реальную цепочку: берёт из API настоящую ссылку на файл обновления и тянет первый мегабайт с CDN Microsoft по IPv4 и IPv6, проверяя поддержку Range и замеряя скорость.

## Нюансы

- **Кэш SHA256** хранится по `md5($localPath)` в `.hash_cache/`. Если переместить файл, кэш не сработает и SHA256 будет пересчитан (а старая запись удалится при очистке осиротевших).
- **Атомарность загрузки**: файл скачивается в `*.tmp` и переименовывается после успеха, поэтому обрыв не портит существующий файл.
- **Дефолтный `latest_pattern`** — `/dvd/i`. Подходит для CentOS Stream и образов, в имени которых есть «dvd». Для других схем переопределите в записи конфига.
- **Кэш формата**: единый `{ "hash": "sha256:<hex>", "mtime": ..., "size": ... }`. Старые записи без префикса `sha256:` корректно нормализуются при чтении.
- **`generate_all_hashes.php` сейчас идёт в один поток.** Хэширование 8-гигабайтного файла занимает 15–30 секунд процессорного времени, для регулярного крона это нормально.
- **mtime файлов** = upstream `Last-Modified` (после загрузки делается `touch`). Это значит «дата релиза», а не «когда скачали» — именно её интерфейс показывает как дату файла.
- **У собранных образов Windows нет апстримной чек-суммы**: их не скачали, а собрали. Целостность гарантируется на уровне исходных пакетов (SHA1 каждого проверяет `aria2`), а SHA256 итогового ISO считается локально после сборки.
- **Пересборка определяется по имени файла**, а не по файлу состояния: номер сборки зашит в имя, поэтому потеря `logs/uup-state.json` не приводит к повторной загрузке и часу конвертации впустую.
- **Права на собранные ISO** — `0644`: это данные, а не программа. Переопределяется через `file_mode` в `config/uup-builds.json`.
